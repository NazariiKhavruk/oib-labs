# Конспект до лабораторної роботи 3: безпечне зберігання паролів

Джерело: Haunts S. *Applied Cryptography in .NET and Azure Key Vault*, розділ 5 (Safely Storing Passwords).

## Завдання 1. Основні положення розділу

**Проблема.** Облікові дані зберігаються в базі, а бази витікають. Тому зберігати треба так, щоб витік не дав зловмиснику самих паролів. Користувачі часто повторюють пароль на різних сайтах, тож витік одного сервісу загрожує й іншим.

**Чого вимагає безпечне зберігання:**
- сервер не повинен мати змоги побачити пароль у відкритому вигляді;
- перевірка пароля йде порівнянням похідного значення, а не самого пароля;
- обчислення має бути достатньо повільним, щоб перебір був дорогим;
- однакові паролі не повинні давати однакові збережені значення.

**Еволюція способів:** відкритий текст → шифрування → простий хеш → хеш із сіллю → хеш із сіллю й багатьма ітераціями (PBKDF2).

## Завдання 2. Способи зберігання: переваги, недоліки, висновок

### 1. Пароль у відкритому вигляді

| Переваги | Недоліки |
|---|---|
| Найпростіша реалізація | Витік бази означає миттєву компрометацію всіх паролів |
| Можна відновити пароль користувачу | Адміністратори й будь-хто з доступом до БД бачать паролі |
| | Пароль потрапляє в логи, резервні копії |

**Висновок:** неприйнятний за жодних умов.

### 2. Шифрування паролів (симетричне)

| Переваги | Недоліки |
|---|---|
| Збережене значення не є паролем у явному вигляді | Потрібен ключ, а його теж треба десь зберігати (проблема переноситься на захист ключа) |
| Пароль можна розшифрувати за потреби | Той, хто отримав ключ (або доступ до сервера), розшифровує всі паролі разом |
| | Сама можливість розшифрувати суперечить меті: сервісу не потрібно знати пароль, лише перевіряти його |
| | Потрібне керування ключами, їх ротація |

**Висновок:** недоцільно. Оборотність є вадою, а не перевагою.

### 3. Простий хеш (MD5, SHA1, SHA256 без солі)

| Переваги | Недоліки |
|---|---|
| Однобічність: пароль не відновлюється з хеша обчисленням | Однакові паролі дають однакові хеші, видно користувачів зі збігом паролів |
| Фіксована довжина, немає ключів для зберігання | Атака за словником і райдужними таблицями: готові таблиці хешів поширених паролів |
| Просто реалізувати (`HashAlgorithm.ComputeHash`) | Універсальні хеші швидкі, GPU перебирає мільярди значень за секунду |
| | MD5 і SHA1 застарілі та мають колізії |

**Висновок:** недостатньо. Це прямо продемонстровано в лабі 2 (відновлення 8-цифрового пароля за MD5).

### 4. Хеш із сіллю (клас `SaltedHash`)

| Переваги | Недоліки |
|---|---|
| Унікальна випадкова сіль на кожного користувача: однакові паролі дають різні хеші | Хеш усе ще швидкий, слабкі паролі перебираються словником для конкретного користувача |
| Райдужні таблиці марні, бо треба окрема таблиця на кожну сіль | Сіль не секретна, її зберігають поряд із хешем |
| Перебір не вдається розпаралелити «одним проходом» на всіх користувачів | Потрібна криптостійка генерація солі (`RandomNumberGenerator`), а не `Random` |

**Висновок:** значно краще за простий хеш і є обов'язковою частиною будь-якої схеми, але сама по собі не захищає від швидкого перебору.

### 5. PBKDF2 (сіль + багато ітерацій, `Rfc2898DeriveBytes`)

| Переваги | Недоліки |
|---|---|
| Сіль плюс настроювана кількість ітерацій (key stretching) уповільнюють кожну спробу перебору | Потребує підбору числа ітерацій: замало слабкий захист, забагато навантаження на сервер |
| Стандарт (RFC 2898 / PKCS #5), вбудований у .NET | Число ітерацій треба підвищувати з ростом потужності заліза |
| Можна обрати алгоритм (SHA1, SHA256, SHA512) | Не вимагає багато пам'яті, тож гірше стійкий до GPU/ASIC, ніж bcrypt, scrypt чи Argon2 |
| Вартість легко виміряти (лаб. 3.4: час від числа ітерацій) | Зберігати треба тріаду: сіль, число ітерацій, алгоритм |

**Висновок:** рекомендований варіант із наявного в .NET без сторонніх бібліотек. Експеримент у завданні 4 показує майже лінійне зростання часу від числа ітерацій, а це й є «ціна» для зловмисника.

## Підсумкова таблиця

| Спосіб | Стійкість до витоку БД | Стійкість до словників/GPU | Рекомендація |
|---|---|---|---|
| Відкритий текст | немає | немає | заборонено |
| Шифрування | залежить від ключа | немає при втраті ключа | не застосовувати |
| Хеш без солі | низька | низька | не застосовувати |
| Хеш із сіллю | помірна | помірна | мінімум, краще PBKDF2 |
| PBKDF2 | висока | висока (з достатнім числом ітерацій) | **застосовувати** |

## Загальний висновок

Паролі не зберігають і не шифрують, а перетворюють однобічною функцією з унікальною випадковою сіллю та великою кількістю ітерацій. У .NET це PBKDF2 через `Rfc2898DeriveBytes`. Число ітерацій має відповідати сучасним рекомендаціям і регулярно підвищуватися, а сіль генеруватися криптостійким генератором. Існують і пам'ятеємні алгоритми (bcrypt, scrypt, Argon2), що стійкіші до апаратного перебору, але виходять за межі розділу.
